Ed 政策与指南

作者：Ethan Ordentlich, Jedidiah Tsang

简介

我们使用 Ed 讨论s 作为课程论坛。如果你对 Ed 不熟悉，请阅读 Ed 使用指南 ，它将帮助你熟悉这个平台。这篇文章包含了一系列关于 Ed 礼仪的指南，我们希望你完整阅读，以便我们所有人都有一个愉快的学期体验！

保持 Ed 包容性

任何在 Ed 等公共论坛上针对、排斥、侮辱或歧视特定个人或群体的内容都将被删除，内容发布者将面临相应的后果。请努力为每个人保持包容的环境。如果你任何时候觉得自己被学生或我们的课程工作人员针对、排斥、侮辱或歧视，请填写我们的 事件报告表 进行报告。如果你不愿意与工作人员交谈，你可以向学校的多个办公室进行举报（ https://diversity.berkeley.edu/report-incident ）。

总体要求

我们不想以"不要做什么"的列表开始，但还是请 不要 ：

发布无用的后续回复
像"+1"和"我也一样"这样的回复毫无意义，只会给所有关注该帖子的人发送烦人的邮件。这些可能会被删除。你可以使用帖子旁边的爱心图标来表达"+1"、感谢等。
使用烦人或误导性的标题
这些是全大写或使用过多标点符号的标题，只是为了吸引用户注意。请保持标题（以及一般内容）描述性强且专业。
发布无关话题或猜测性内容或钓鱼内容
与课程无关和/或非教育性的内容不属于 Ed。猜测性的、制造 drama 的或故意误导的内容会阻碍课程工作人员和其他学生之间的有效沟通。
如果自己解决了问题却说"算了"或"已解决"
论坛是集体知识的宝贵来源。自己回答问题是有效的，也是对集体知识的贡献。每个人都讨厌有人在回复自己问题时说类似 "算了，我自己解决了！" ，或者 根本不回答 。其他学生如果遇到同样的问题，就无法从中学习。相反，请添加包含你的解决方案的回答或评论！

为什么要使用论坛？

杜克/北卡州立/UNC/UF 的最新研究 表明，学生在课程论坛（如 Piazza 和 Ed）上的参与，在学生提出 建设性问题 时最为有益，这些问题反映了他们解决问题的推理和尝试。通过创建和提出这些建设性问题，学生正在练习他们的 元认知 技能，或者说是他们 思考如何处理问题和学习 的方式。

论坛也是寻求异步帮助的有效方式。办公时间和实验课并不总是在进行，与 TA 同步交流也并不总是可能的。相反，你可以在 Ed 上提问，同时继续做其他事情，等待回复。

此外，论坛和其他异步求助方式在许多现实世界的场景中也是广泛使用的工具，从 StackOverflow 到公司内部工单系统。

计算机科学 61B 论坛政策

论坛的许多好处只有在我们都适当和有效地使用它，并投入工作来维护其质量时才能实现。

分类

CS 61B 有很多学生，肯定会有很多帖子。为了组织这些帖子，我们使用 Ed 分类 。要在 Ed 上发帖或提问，你 必须 选择一个合适的分类。

分类概述如下：

物流
关于课程一般性问题。
讲座
关于每个讲座内容的问题。此分类有一个模板，要求提供讲座编号。
项目、实验、作业
关于作业的调试帮助的问题和请求。这些分类有每个作业的子分类。每个子分类还有子子分类，用于区分私人调试问题（Gitbugs）和各种公开问题。例如， Projects - Project 1 - Gitbugs 和 Projects - Project 1 - Conceptual (Circular Buffer) 。
讨论
关于讨论工作表的题和概念性澄清。此分类有每周的子分类。
考试
关于考试物流、历年考试以及与考试相关的任何问题。随着考试临近，我们将添加额外的分类来提问关于历年考试的问题。
其他
任何不适合上述分类的关于课程的问题都可以放在这里。
社交
想组建学习小组或举办学习会议？在这里发帖。
外部公告
来自与 CS 61B 无关的外部团体的任何帖子都将发布在此分类中。此分类中的帖子必须经课程工作人员批准。

如何提问，如何不提问

不幸的是，在 Ed 上寻求帮助比较慢，因为我们不能在论坛上花费所有时间。在你寻求帮助之前，你应该尝试自己回答你的问题！我们也希望你学会如何帮助自己，这在某些情况下比问工作人员更慢，但从长远来看会更有益。可以帮助你做到这一点的资源包括：

Ed 上的先前问题。
你可以使用 Ed 的搜索功能在分类内搜索，这样你就不必浏览所有内容。
官方课程材料
作业规范是一个很好的信息来源。此外，每个作业都会从页面顶部链接一个 常见问题 。FAQ 将在作业运行期间更新，所以要经常查看！课程工作人员也会在学生作业时为作业创建一些补充材料，因为我们会发现学生遇到困难的地方。
Google 或你选择的搜索引擎。
虽然搜索 Google 可能看起来不像"独立编程"，但专业程序员经常在网上搜索类似问题的解决方案。现在学习好的搜索技术将在学期剩余时间和你的职业生涯中得到回报。 但这不包括搜索解决方案代码。不要那样做。

但是，你不应该在一个问题上花费数小时 ，你应该寻求帮助，可能在论坛上。当你在 Ed 上寻求帮助时，以下是你可以做的一些事情，以确保你收到的回复更有可能解决你的问题。

解释你的问题是什么，以及你认为什么会帮助你继续前进。
课程工作人员不会读心术。我们不会神奇地知道哪里出了问题，或者你想回答什么。

如果你的问题没有包含足够的信息让我们能够回答，或者没有向我们展示你到目前为止尝试了什么，我们会询问。你整体上会得到较慢的回复，但你也会学会如何改进你未来的问题以获得更快的回复。

同样，有一些事情你不应该做 来获得回复：

要求"提示"或"答案"
我们不知道你想要什么样的提示，或者你试图完成什么。我们甚至不知道你是否在这个问题上工作过，或者你是否看到了错误就立即提问。

我们不会给答案，而是会问一个后续问题来澄清你在问什么。

说"我什么都不懂"
这很难，有时不可能给出答案。相反，你应该尝试找出你不理解的起点。如果你无法开始，这仍然是一个有效的问题——而且与"任何事情"完全不同。

部分材料来自 Adam Blank 的 "如何寻求帮助" 指南。

概念性帖子

通常，你会有关于实验或项目中的概念性问题，或者关于讨论、历年考试或外部资源的问题。以下是一些你应该遵循的指南，以更快获得有用的答案：

不要问你的解决方案"是否正确"
相反，解释你为什么认为你的解决方案是正确的，并指出你不确定的任何部分。重建你的论点需要工作人员做很多工作，所以向我们解释你的思路可以帮助你获得更好的答案，并解决你可能存在的任何误解。

私人调试帮助，或 Gitbugs

有时，你可能遇到需要向课程工作人员展示代码的问题。但是，根据我们的 合作政策 ，你不能公开发布代码，包括在公开 Ed 帖子上。相反，你可以使用每个作业的 Gitbugs 分类来发布私人调试帖子。

以下是专门针对私人调试问题的指南：

链接你的 GitHub 仓库并推送。
有时（但并非总是），我们会查看你的代码。这确保我们能够轻松查看最新版本。
提供你有问题的那部分代码的截图。
我们要求你提供截图，这样我们就知道你在看代码的哪一部分。
在描述你的 bug 时，要具体。
"一切"、"它不工作"、"自动评分失败"、"我不知道"等描述都不够具体。没有具体信息我们无法提供帮助。至少，你应该告诉我们哪个测试失败了，或者你看到什么错误，尽管仅此一项并不能保证第一个回复会有帮助。

如果你能识别出一小块代码，比如一个方法或几行代码，不符合你的预期，那很好——告诉我们你发现了什么，以及你困惑的地方！

我们期望你已经尝试过调试。告诉我们你学到了什么。
这与上面的指南相辅相成！如果我们看不出你尝试过调试，我们不会为你调试，而是会问你尝试了什么。这可以是打印调试，或使用 IntelliJ 调试器。截图在这里非常有用，只要你解释我们在看什么！

Ed 使用技巧

更改你的电子邮件设置以接收更少的邮件。
在右上角，点击你的头像，然后"设置"，然后点击"通知"来调整你从 Ed 收到的电子邮件数量。公告邮件将始终发送给你。
关注你想了解更多的主题帖子。
如果你看到一个你想继续跟踪的正在进行的问题，你可以：
  • 点击问题右上角的"Watch"选项以接收电子邮件更新，或
  • "Star"问题右上角的帖子，以将其固定在你的 Ed 上。
引用其他问题、回答和评论
使用 #N（例如 #1 或 #1c）是引用其他线程的简洁方式。你可以用它来回答重复的问题，或指向你尝试过但不工作的东西。
使代码（和堆栈跟踪）可读。
使用编辑器工具栏中的可运行代码按钮，这样你的代码看起来更好。语法高亮的代码比纯文本代码更容易阅读。

如果你有不想让其他学生看到的个人问题，请发布私人帖子。私人帖子只对课程工作人员可见。如果你只希望首席 TA 和 Josh 看到你的问题，请发送电子邮件至 cs61b [at] berkeley.edu
